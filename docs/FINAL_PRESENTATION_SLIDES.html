SECTION 1 • BACKGROUND & PROBLEM

1. แนวคิดและที่มาของโครงงาน (Problem Statement)

02 / 15
4 ปัญหาวิกฤตของการเดินทางในปัจจุบัน

1. ภาระค่าน้ำมันและค่าผ่านทางสูง: ขับคนเดียวต้นทุนต่อกิโลเมตรสูง

2. วิกฤตจราจรในงานอีเวนต์/คอนเสิร์ต: รถหลั่งไหลเข้ามาพร้อมกัน ที่จอดรถไม่เพียงพอ ติดขัดสะสมนับชั่วโมง

3. รถรับจ้างสาธารณะขาดแคลน & โก่งราคา: ปัญหารถปฏิเสธผู้โดยสารและ Surge Pricing 200–300% ช่วงเลิกงาน

4. มลพิษคาร์บอนฟุตพริ้นท์ ($CO_2$): รถยนต์ปล่อย $CO_2$ เฉลี่ย 120 กรัม/กม./คัน ซ้ำเติมสภาวะโลกร้อน

ทางออก: ระบบคาร์พูลแบ่งปันต้นทุนตามจริง (True Carpooling)

• เน้นผู้มีเส้นทางเดียวกัน: คนขับตั้งใจเดินทางไปจุดหมายนั้นอยู่แล้ว เปิดรับเพื่อนร่วมทางเพื่อหารค่าน้ำมันตามจริง

• ประหยัดค่าใช้จ่าย 50–70%: ค่าโดยสารถูกกว่าเรียกรถรับจ้างทั่วไปอย่างชัดเจน และไม่มีค่าบริการแสวงหากำไร

• ความปลอดภัยหลายชั้น (Multi-layer Safety): ยืนยันตัวตน KYC + ตรวจสอบภาพถ่ายป้ายทะเบียนรถจริงก่อนให้บริการ

• Green Travel & ESG: แสดงสถิติจำนวนกิโลกรัม $CO_2$ ที่ลดได้ และเทียบเคียงเป็นจำนวนต้นไม้

SECTION 1 • STRATEGY & OBJECTIVES

1. เปรียบเทียบความแตกต่าง และ 5 วัตถุประสงค์หลัก

03 / 15
Carpooling (Iko-Share) vs Ride-Hailing (Grab/Bolt)
มิติเปรียบเทียบ Ride-Hailing เชิงพาณิชย์ Iko-Share Carpooling
เจตนาเดินทาง วิ่งรถวนเพื่อหารายได้เชิงพาณิชย์ เดินทางไปทิศทางเดียวกันอยู่แล้ว
โครงสร้างราคา แสวงหากำไร + มี Surge Pricing หารต้นทุนจริง (Fair Share)
สถานะกฎหมาย ต้องจดทะเบียนรถสาธารณะ แบ่งปันค่าใช้จ่ายถูกต้องตามกฎหมาย
สิ่งแวดล้อม เพิ่มจำนวนเที่ยววิ่งบนถนน ลดจำนวนรถ + คำนวณ $CO_2$ Offset
5 วัตถุประสงค์หลักของโครงงาน (Objectives)

1. แพลตฟอร์มคาร์พูลสู่อีเวนต์: พัฒนา Web Application จับคู่คนขับและผู้โดยสารอย่างมีประสิทธิภาพ

2. คำนวณราคาเป็นธรรม (Fair Share): คิดราคาแนะนำจากระยะทางจริง (น้ำมัน 2.20 บ./กม. + สึกหรอ 1.30 บ./กม.)

3. ความปลอดภัยระดับสูง: ยืนยันตัวตน (KYC), แอดมินตรวจสอบภาพป้ายทะเบียนรถจริง และระบบรีวิวสองทาง

4. PDPA Compliance 100%: ขอความยินยอมจัดเก็บภาพป้ายทะเบียน, จัดการคุกกี้ และหน้าจัดการสิทธิข้อมูลส่วนบุคคล

5. ส่งเสริมการท่องเที่ยวสีเขียว: แสดงผลการลดก๊าซ $CO_2$ เทียบเคียงจำนวนต้นไม้ที่ฟื้นฟูสิ่งแวดล้อม

SECTION 2 • TECH STACK & ARCHITECTURE

2. เหตุผลเชิงวิชาการในการเลือกเทคโนโลยี (Tech Stack Justification)

05 / 15
เทคโนโลยีที่เลือก เหตุผลและบทบาทในระบบ Iko-Share ทำไมไม่เลือกเทคโนโลยีอื่น?
React 18 + Vite SPA สถาปัตยกรรม Component-driven, HMR รวดเร็ว, ทำ Code Splitting อัตโนมัติ CRA ล้าสมัย ช้า ส่วน Next.js ซับซ้อนเกินจำเป็นสำหรับ Single Page App
Tailwind CSS (120 FPS) Utility-first ช่วยให้ Purged Bundle มีขนาดเล็กมาก และใช้ GPU Hardware Acceleration UI Component Libraries สำเร็จรูปเทอะทะและ Re-render บ่อยทำให้กระตุก
Node.js & Express.js Non-blocking Event-driven I/O รองรับ REST API และ Real-time Streaming ได้ดีเยี่ยม Spring Boot/Java ใช้ทรัพยากรสูงและ Deploy บน Cloud Serverless ได้ช้ากว่า
PostgreSQL 16 (Supabase) Relational Integrity (ACID), Foreign Keys, Check Constraints, มี Connection Pooler NoSQL (MongoDB) ขาดความเข้มงวดในการควบคุมสถานะการจองและธุรกรรมการเงิน
Server-Sent Events (SSE) ใช้ HTTP ปกติ, รองรับ HTTP/2 Multiplexing, มี Auto-reconnect ในตัว, ประหยัดทรัพยากร WebSocket ต้องรักษา State ตลอดเวลา ซึ่งขัดแย้งกับ Vercel Serverless Functions
Google Maps Embed API ฐานข้อมูลสถานที่ ถนน และจุดนัดพบในไทยแม่นยำ 100% พร้อมปุ่มเปิดแอป GPS นำทาง OpenStreetMap มีปัญหา Geocoding ชื่อเฉพาะภาษาไทย ปักหมุดหลุดไปต่างประเทศ

SECTION 3 • REQUIREMENTS

3. ข้อกำหนดเชิงหน้าที่ (Functional Requirements: 10 Core Modules)

06 / 15
FR 01 - 05 การเดินทาง ยานพาหนะ และแผนที่

• FR-01: Authentication & Role RBAC: สมัครสมาชิก, เข้ารหัส JWT, จัดการ 4 บทบาท (Passenger, Driver, Both, Admin)

• FR-02: Vehicle Plate Verification: ลงทะเบียนรถ แนบภาพถ่ายป้ายทะเบียนจริง และกดยินยอมข้อตกลง PDPA ให้แอดมินอนุมัติ

• FR-03: Trip Management Engine: สร้างทริปคาร์พูล กำหนดจุดแวะรับส่ง (Waypoints), จำนวนที่นั่ง, เวลา และเงื่อนไขการเดินทาง

• FR-04: Smart Fair Price Calculator: คำนวณราคาแนะนำต่อที่นั่งตามระยะทางจริง (สูตรค่าน้ำมัน + ค่าสึกหรอ)

• FR-05: Interactive Route & GPS Map: แผนที่ Google Maps แสดงเส้นทางจริง สภาพจราจร และปุ่มเปิด GPS บนสมาร์ตโฟน

FR 06 - 10 การจอง ชำระเงิน แชท และความปลอดภัย

• FR-06: Booking Lifecycle State Machine: ระบบขอจองที่นั่ง, ตรวจสอบ, อนุมัติ/ปฏิเสธ พร้อมหักและคืนที่นั่งว่างอัตโนมัติ

• FR-07: PromptPay QR & Slip Verification: สร้าง EMVCo QR Code อัตโนมัติ ผู้โดยสารแนบสลิป และคนขับกดยืนยัน

• FR-08: In-Trip SSE Realtime Group Chat: แชทเฉพาะสมาชิกในทริป พุชข้อความด้วย Server-Sent Events พร้อม Fallback Polling 15 วิ

• FR-09: Mutual Peer Review: ระบบประเมินและให้คะแนนดาว 1–5 แก่เพื่อนร่วมทางหลังจบทริปเพื่อสร้างความน่าเชื่อถือ

• FR-10: PDPA Rights & Eco ESG Analytics: หน้าจัดการสิทธิขอรับ/ลบข้อมูลส่วนบุคคล, Cookie Consent, และสถิติคาร์บอน $CO_2$

SECTION 4 • WORKFLOW & LIFECYCLE

4. วงจรสถานะการจองที่นั่ง (Booking Lifecycle State Machine)

09 / 15
แผนภาพสถานะการจอง (State Transition Diagram)
ความถูกต้องของวงจรข้อมูลและการคืนที่นั่ง

1. การจัดสรรที่นั่งว่างแบบ Real-Time: เมื่อคนขับกด "อนุมัติ" ระบบจะทำการหักที่นั่งว่าง (available_seats = available_seats - 1) ในระดับ Atomic Transaction ป้องกันปัญหาที่นั่งเกิน

2. ระบบคืนที่นั่งอัตโนมัติ (Auto-Release): หากผู้โดยสารกดยกเลิกการเดินทาง หรือคนขับกดคัดชื่อออกเนื่องจากทำผิดข้อตกลง ระบบจะคืนที่นั่งว่างกลับสู่ทริปทันที

3. Access Guard ในห้องแชทประจำทริป: สิทธิ์การเข้าห้องแชทและสนทนาผ่าน SSE Stream จะปลดล็อกเฉพาะผู้ที่มีสถานะ 'จองแล้ว' และหัวหน้าทริปเท่านั้น

4. การเปิดระบบรีวิว: เมื่อทริปมีสถานะ 'completed' ระบบจะเปิดหน้าต่างให้รีวิวและประเมินดาว 1–5 แก่กัน

วิธีแก้: ยกระดับสู่ Google Maps Embed API ครอบคลุมสถานที่ภาษาไทย 100% พร้อมปุ่มเปิดแอป GPS นำทาง
2. Serverless Runtime กับ Real-time Chat
ปัญหา: Serverless บน Vercel ทำงานแบบ Stateless ไม่รองรับ WebSocket ที่ต้องค้าง State การเชื่อมต่อตลอดเวลา
วิธีแก้: เลือกใช้ Server-Sent Events (SSE) สตรีมข้อความใหม่ทางเดียวร่วมกับ Fallback Polling (15 วิ)
3. ความปลอดภัยของยานพาหนะและกฎหมาย PDPA
ปัญหา: ต้องยืนยันป้ายทะเบียนรถจริง แต่ภาพป้ายทะเบียนเป็นข้อมูลส่วนบุคคลตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562
วิธีแก้: บังคับยินยอมผ่าน Vehicle PDPA Consent Modal และเก็บภาพเป็นความลับเฉพาะแอดมินตรวจสอบ
4. In-flight API Request Spams
ปัญหา: ผู้ใช้กดปุ่มย้ำหรือเปลี่ยนหน้าเร็วเกินไป ทำให้เบราว์เซอร์ส่ง HTTP GET Request ข้อมูลเดิมซ้ำซ้อนในระดับมิลลิวินาที
วิธีแก้: ออกแบบระบบ In-Flight Promise Sharing ใน API Client ตัดคำขอซ้ำซ้อนทิ้งทันที

บทสรุปสำหรับผู้บริหาร (Executive Summary)

โครงงาน Iko-Share ถูกพัฒนาขึ้นเพื่อแก้ไขปัญหาวิกฤตค่าใช้จ่ายในการเดินทาง ปัญหาการจราจรติดขัด และปัญหาการปล่อยก๊าซเรือนกระจกจากการเดินทางสู่งานอีเวนต์ คอนเสิร์ต และสถานที่ท่องเที่ยว ด้วยการสร้างแพลตฟอร์มคาร์พูล (Carpooling) อัจฉริยะที่ยึดหลัก "การแบ่งปันต้นทุนตามจริง (True Cost-Sharing)" ระบบได้รับการออกแบบภายใต้สถาปัตยกรรม 3-Tier Architecture ประกอบด้วย Client Tier (React 18 + Tailwind CSS 120 FPS), Application Tier (Node.js + Express.js Serverless Gateway บน Vercel) และ Data Tier (PostgreSQL บน Supabase Cloud) ระบบรองรับ 10 ฟังก์ชันแกนหลัก เช่น แผนที่ Google Maps แบบโต้ตอบ, ห้องแชทเรียลไทม์ผ่าน SSE, การยืนยันสลิป PromptPay EMVCo, ระบบตรวจสอบภาพถ่ายป้ายทะเบียนรถยนต์ที่สอดคล้องกับ PDPA 100% และระบบคำนวณการลดก๊าซ $CO_2$ ผ่านการทดสอบ 165 Test Cases ด้วย Pass Rate 97.0% ปราศจากข้อบกพร่องระดับวิกฤต

1. แนวคิดหรือที่มาของโครงงาน (Project Background & Rationale)

1.1 สภาพปัญหาและความสำคัญ (Problem Statement)

ในยุคปัจจุบัน การเดินทางไปยังงานกิจกรรมขนาดใหญ่ (Event) เช่น คอนเสิร์ต เทศกาลดนตรี งานรับปริญญา มหกรรมกีฬา ตลอดจนการท่องเที่ยวข้ามจังหวัด ประสบปัญหาสำคัญ 4 ประการที่ส่งผลกระทบต่อทั้งเศรษฐกิจ คุณภาพชีวิต และสิ่งแวดล้อม:

1. ภาระค่าใช้จ่ายในการเดินทางสูง

ราคาน้ำมันเชื้อเพลิงและค่าผ่านทางปรับตัวสูงขึ้น การขับรถยนต์ส่วนบุคคลคนเดียวทำให้เกิดต้นทุนเฉลี่ยต่อคนต่อกิโลเมตรสูง และสร้างภาระทางการเงินที่ไม่จำเป็น

2. ปัญหาการจราจรและพื้นที่จอดรถไม่เพียงพอ

ช่วงเวลาจัดงานอีเวนต์ขนาดใหญ่และแหล่งท่องเที่ยว ยานพาหนะหลั่งไหลเข้ามาพร้อมกัน ทำให้เกิดการจราจรติดขัดสะสมนับชั่วโมง และพื้นที่จอดรถรองรับได้ไม่เพียงพอ

3. ปัญหารถสาธารณะขาดแคลนและการโก่งราคา

หลังเลิกงานอีเวนต์หรือในพื้นที่ต่างจังหวัด มักพบการปฏิเสธผู้โดยสาร หรือการปรับขึ้นค่าบริการสูงเกินจริง (Surge Pricing 200–300%) ของรถรับจ้างสาธารณะ

4. มลพิษและก๊าซเรือนกระจก ($CO_2$)

การใช้รถยนต์แยกคันก่อให้เกิดการปล่อยก๊าซคาร์บอนไดออกไซด์เฉลี่ย 120 กรัม/กม. ต่อคัน เร่งวิกฤตการเปลี่ยนแปลงสภาพภูมิอากาศ (Global Warming)

1.2 นิยามและความแตกต่างระหว่าง Carpooling กับ Ride-Hailing

ในประเทศไทย ประชาชนมักสับสนระหว่าง Ride-Hailing เชิงพาณิชย์ (เช่น Grab, Bolt) กับ Carpooling (การร่วมเดินทาง) ทางทีมพัฒนาจึงได้วางกรอบแนวคิดให้ Iko-Share เป็น True Carpooling Platform อย่างเคร่งครัด:

คุณลักษณะ บริการ Ride-Hailing เชิงพาณิชย์ (Grab, Bolt) Iko-Share (True Cost-Sharing Carpooling)
เจตนาการเดินทาง คนขับวิ่งรถวนเพื่อแสวงหาลูกค้าและสร้างรายได้เชิงพาณิชย์ คนขับมีแผนเดินทางไปยังจุดหมายนั้นอยู่แล้ว และเปิดรับเพื่อนร่วมทาง
โครงสร้างราคา คิดราคาแสวงหากำไร + มีระบบ Surge Pricing เมื่ออุปสงค์สูง หารต้นทุนค่าน้ำมันและค่าสึกหรอตามจริง (Fair Share Formula) ปราศจากค่าบริการแพลตฟอร์มส่วนเพิ่ม
สถานะทางกฎหมาย ต้องใช้ใบขับขี่สาธารณะและจดทะเบียนรถรับจ้างสาธารณะ การแบ่งปันค่าใช้จ่ายระหว่างผู้มีเส้นทางเดียวกัน (Cost-sharing) ถูกต้องตามหลักสิทธิเสรีภาพและกฎหมายไทย
มิติทางสิ่งแวดล้อม เพิ่มจำนวนเที่ยววิ่งของรถบนถนน (Empty deadheading trips) ลดจำนวนรถยนต์บนท้องถนนโดยตรง (Maximize Occupancy) และคำนวณ $CO_2$ ที่ลดได้จริง

1.3 วัตถุประสงค์ของโครงงาน (Project Objectives)

  1. เพื่อพัฒนาเว็บแอปพลิเคชันแบ่งปันการเดินทาง (Carpooling Web Application): ที่ช่วยจับคู่ผู้ขับขี่และผู้โดยสารที่มีจุดหมายปลายทางหรือเส้นทางร่วมกันได้อย่างมีประสิทธิภาพและใช้งานง่าย
  2. เพื่อพัฒนาระบบคำนวณราคาแนะนำที่เป็นธรรม (Fair Share Pricing Model): ประเมินต้นทุนค่าน้ำมันและค่าเสื่อมสภาพตามระยะทางจริง โดยกำหนดเพดานราคาป้องกันการแสวงหากำไรเกินควร
  3. เพื่อสร้างมาตรฐานความปลอดภัยหลายชั้น (Multi-Layer Safety Standard): ยืนยันตัวตนสมาชิก (KYC), การตรวจสอบภาพถ่ายป้ายทะเบียนรถจริงโดยผู้ดูแลระบบ และระบบรีวิวเพื่อนร่วมทางแบบสองทาง (Mutual Peer Review)
  4. เพื่อปฏิบัติตามกฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA Compliance 100%): ขอความยินยอมในการจัดเก็บภาพถ่ายยานพาหนะ จัดการคุกกี้ และจัดทำระบบรองรับการใช้สิทธิของเจ้าของข้อมูลส่วนบุคคล (Data Subject Rights)
  5. เพื่อส่งเสริมการท่องเที่ยวและการเดินทางสีเขียว (Green Travel & ESG Promotion): แสดงผลการลดการปล่อยก๊าซคาร์บอนไดออกไซด์ ($CO_2$) และเทียบเคียงเป็นจำนวนต้นไม้ที่ช่วยฟื้นฟูสิ่งแวดล้อม

ภาพที่ 2.1: แผนผังสถาปัตยกรรม 3-Tier Architecture ฉบับสมบูรณ์ที่ปรับปรุงตามระบบจริง (Components + Tools + 3rd-Party Final Version)

2.1 รายละเอียดการทำงานของแต่ละ Tier

  • 1. Presentation Tier (Client Layer): พัฒนาด้วย React 18 และบันเดิลด้วย Vite มีโครงสร้างแบบ Single Page Application (SPA) ใช้ Tailwind CSS ร่วมกับเทคนิคการเร่งกราฟิกด้วยฮาร์ดแวร์ GPU (Hardware-accelerated) ทำให้ได้ความลื่นไหลระดับ 120 FPS ตัดปัญหากระตุกในหน้าจอสมาร์ตโฟน มีระบบ In-Flight API Request Deduplication ในตัว ช่วยลดการยิง API ซ้ำซ้อน และใช้ React Context API จัดการสถานะสิทธิ์และการสลับภาษา (TH/EN)
  • 2. Application Tier (Business Logic Layer): รันบน Node.js + Express.js ผ่านโครงสร้าง Vercel Serverless Functions ทำหน้าที่ประมวลผลกฎทางธุรกิจทั้งหมด มีระบบความปลอดภัยด้วย Helmet (HTTP Security Headers), express-rate-limit ป้องกัน Brute-force/DDoS, JWT Stateless Authentication, และโมดูลบริการหลัก เช่น การคำนวณราคาเฉลี่ยที่เป็นธรรม, การกระจายข้อความแชทผ่าน Server-Sent Events (SSE), และระบบตรวจสอบความยินยอม PDPA
  • 3. Data Tier (Persistence & Storage Layer): ใช้ฐานข้อมูลเชิงสัมพันธ์ PostgreSQL 16 บน Supabase Cloud Platform พร้อมตัวจัดการการเชื่อมต่อ (Connection Pooler) จัดโครงสร้างข้อมูลตามหลัก 3NF ครบ 14 ตาราง และเชื่อมโยงกับ Supabase Storage (S3-Compatible) ในการจัดเก็บไฟล์ภาพเอกสารสำคัญ เช่น รูปถ่ายป้ายทะเบียนรถยนต์สำหรับตรวจสอบ, รูปภาพสลิปโอนเงิน และเอกสาร KYC

3. Functional & Non-Functional Requirements ที่ได้ออกแบบไว้

3.1 Functional Requirements (ข้อกำหนดเชิงหน้าที่ 10 โมดูลหลัก)

รหัส FR ชื่อโมดูลฟังก์ชัน รายละเอียดการทำงานที่ออกแบบและพัฒนาจริง
FR-01 ระบบยืนยันตัวตนและจัดการบทบาท (Auth & RBAC) รองรับการลงทะเบียน, เข้าสู่ระบบด้วย JWT Token, รีเซ็ตรหัสผ่าน, และจัดการ 4 บทบาท: ผู้โดยสาร (Passenger), คนขับ (Driver), สองบทบาท (Both), และผู้ดูแลระบบ (Admin)
FR-02 ระบบลงทะเบียนรถและตรวจสอบป้ายทะเบียน คนขับลงทะเบียนยี่ห้อ รุ่น ความจุ และอัปโหลดภาพถ่ายป้ายทะเบียนรถจริงเข้าสู่สถานะ "รอดำเนินการ" พร้อมกล่องขอความยินยอม PDPA ให้แอดมินตรวจสอบก่อนเปิดใช้ทริป
FR-03 ระบบสร้างและจัดการเที่ยวเดินทาง (Trip Engine) กำหนดต้นทาง-ปลายทาง, เวลาออกเดินทาง, จุดแวะรับส่ง (Waypoints), จำนวนที่นั่งว่าง, เงื่อนไขผู้โดยสาร, และสไตล์การขับขี่ของคนขับ
FR-04 ระบบประเมินเส้นทางและราคาแนะนำเป็นธรรม (Fair Share) ประเมินระยะทางและเวลาอัตโนมัติ (Google Directions / Spatial Fallback) พร้อมคิดราคาแนะนำต่อที่นั่งตามสูตรต้นทุนน้ำมัน (2.20 บ./กม.) + ค่าสึกหรอ (1.30 บ./กม.)
FR-05 ระบบแผนที่นำทางแบบโต้ตอบ (Interactive Route Map) เชื่อมต่อ Google Maps Embed API แสดงเส้นทางจริง สภาพจราจร จุดแวะพัก และมีปุ่มเปิดระบบ GPS นำทางตรงสู่สมาร์ตโฟน
FR-06 วงจรการจองที่นั่ง (Booking Lifecycle State Machine) ผู้โดยสารส่งคำขอจอง, คนขับตรวจสอบและกดอนุมัติ/ปฏิเสธ, จัดการตัดและคืนที่นั่งว่างอัตโนมัติตามวงจรสถานะอย่างถูกต้อง
FR-07 การชำระเงินและตรวจสอบสลิป (PromptPay QR & Slip) สร้าง Dynamic QR Code มาตรฐาน BOT EMVCo ตามยอดเงินค่าโดยสาร ผู้โดยสารอัปโหลดสลิปโอนเงิน และคนขับกดยืนยันการรับเงิน
FR-08 ห้องแชทเรียลไทม์ประจำทริป (In-Trip SSE Chat) เฉพาะคนขับและผู้โดยสารที่ได้รับการอนุมัติเท่านั้นที่เข้าห้องแชทได้ พุชข้อความด้วย Server-Sent Events แบบ Real-time พร้อม Fallback Polling 15 วิ
FR-09 ระบบรีวิวเพื่อนร่วมทาง (Mutual Peer Review) เปิดให้คนขับและผู้โดยสารประเมินคะแนน 1–5 ดาว และข้อความรีวิวซึ่งกันและกันหลังการเดินทางสำเร็จ เพื่อสร้างคะแนนความน่าเชื่อถือ
FR-10 การคุ้มครองข้อมูลส่วนบุคคลและสิ่งแวดล้อม (PDPA & ESG) มีหน้าขอใช้สิทธิ PDPA (ลบ/ส่งออกข้อมูล), จัดการ Cookie Consent, และแสดงสถิติการลด $CO_2$ พร้อมจำนวนต้นไม้ที่ช่วยฟื้นฟู

3.2 Non-Functional Requirements (ข้อกำหนดเชิงคุณภาพ 5 ด้าน)

1. ประสิทธิภาพและความลื่นไหล (Performance)

• หน้าเว็บโหลดครั้งแรก (FCP) ภายใน 1.0 วินาที และ LCP ภายใน 1.8 วินาที
• หน้าแรกทำงานด้วย GPU Hardware Acceleration ลื่นไหลระดับ 60/120 FPS ไร้การ Re-render ซ้ำซ้อน
• บีบอัดข้อมูล API ด้วย Gzip/Deflate ลดขนาดทราฟฟิกเครือข่ายลง 70–85%

2. ความมั่นคงปลอดภัยและการรักษาความลับ (Security)

• เข้ารหัสรหัสผ่านด้วย bcryptjs (Salt Rounds 10)
• ป้องกัน SQL Injection 100% ด้วย Parameterized Queries ($1, $2)
• ติดตั้ง Helmet ป้องกัน XSS/Clickjacking และ Rate Limiter ป้องกันการสแปม

3. ความพร้อมใช้งานและการขยายตัว (Scalability)

• สถาปัตยกรรม Serverless บน Vercel รองรับ Auto-scaling ตามปริมาณผู้ใช้งานจริง
• Supabase PostgreSQL Connection Pooler รองรับโหลดการเรียกใช้สูงพร้อมกัน

4. ความสะดวกในการใช้งานและการเข้าถึง (Usability)

• Fully Responsive Design 100% ครอบคลุม Mobile, Tablet และ Desktop
• รองรับการสลับภาษา ไทย / อังกฤษ และธีมสี Morning Forest สบายตา

4. Use Case Model

4.1 ผู้มีบทบาทในระบบ (Actors Definition)

1. ผู้โดยสาร (Passenger)

ค้นหาทริป, ตรวจสอบรายละเอียดและแผนที่, ส่งคำขอจองที่นั่ง, สแกน QR ชำระเงิน, แนบสลิป, แชทในทริป, และรีวิวคนขับ

2. คนขับรถ (Driver)

ลงทะเบียนรถยนต์, อัปโหลดภาพป้ายทะเบียนและยินยอม PDPA, สร้างทริป, อนุมัติการจอง, ตรวจสอบสลิปโอนเงิน, และรีวิวผู้โดยสาร

3. ผู้ดูแลระบบ (Admin)

ตรวจสอบภาพถ่ายป้ายทะเบียนรถยนต์, อนุมัติเอกสาร KYC, จัดการรายงานข้อความแชท และดำเนินการคำร้องขอด้านสิทธิ PDPA

5.1 การเพิ่มประสิทธิภาพฐานข้อมูลด้วย B-Tree Indexing

เพื่อรองรับการสืบค้นข้อมูลที่มีความถี่สูงและป้องกันปัญหาคอขวด (Database Bottleneck) ระบบได้สร้าง B-Tree Indexes บนคอลัมน์สำคัญ:

  • idx_trips_departure_time: เร่งความเร็วการค้นหาและเรียงลำดับเที่ยวเดินทางตามวันและเวลา
  • idx_trips_trip_status: ช่วยให้คัดกรองเฉพาะทริปที่ยังเปิดให้บริการ (active) ได้ในระดับเวลา Sub-millisecond
  • idx_cars_user_id & idx_cars_verification_status: ดึงข้อมูลรถของผู้ใช้และรถที่รอการตรวจสอบของแอดมิน
  • idx_bookings_trip_id: โหลดรายชื่อผู้โดยสารและสถานะการชำระเงินของแต่ละทริปอย่างรวดเร็ว
  • idx_notifications_user: ดึงข้อความแจ้งเตือนส่วนบุคคลเรียงจากล่าสุดได้ทันทีโดยไม่ต้อง Full Table Scan

7. Conclusion (ปัญหา อุปสรรค และแนวทางการพัฒนาต่อยอด)

7.1 สรุปผลสัมฤทธิ์ของโครงงาน (Project Achievements)

การดำเนินโครงงาน Iko-Share ประสบความสำเร็จตามวัตถุประสงค์ที่กำหนดไว้อย่างสมบูรณ์ ทีมพัฒนาสามารถสร้างแพลตฟอร์มคาร์พูลต้นแบบที่ใช้งานได้จริง (Working Production Prototype) ภายใต้สถาปัตยกรรม 3-Tier Architecture ที่มีความเสถียรและปลอดภัย ระบบช่วยลดภาระค่าใช้จ่ายในการเดินทางของผู้ใช้งานได้ถึง 50–70% เมื่อเทียบกับบริการรถรับจ้างส่วนบุคคล ช่วยบรรเทาวิกฤตการจราจรและปัญหาที่จอดรถในงานอีเวนต์ และสร้างแรงจูงใจในการลดการปล่อยก๊าซเรือนกระจกสู่ชั้นบรรยากาศ

7.2 ปัญหา อุปสรรคที่พบระหว่างการพัฒนา และแนวทางแก้ไข (Challenges & Resolutions)

ปัญหา/อุปสรรคที่พบ ผลกระทบต่อระบบ แนวทางการแก้ไขที่ได้ดำเนินการจริง
1. ข้อจำกัดของ OpenStreetMap กับสถานที่ภาษาไทย การค้นหาชื่อเฉพาะภาษาไทย เช่น "วค.สุราษฎร์ธานี", มหาวิทยาลัย, จุดนัดพบในต่างจังหวัด มีพิกัดเพี้ยนหลุดไปต่างประเทศ ยกระดับไปใช้ Google Maps Embed API & Directions ซึ่งมีฐานข้อมูลสถานที่และเครือข่ายถนนในไทยสมบูรณ์ 100% พร้อมปุ่มกดเปิด GPS นำทาง
2. ความท้าทายของ Serverless กับ Real-time Chat โครงสร้าง Serverless Functions (Vercel) ทำงานแบบ Stateless ไม่รองรับ WebSocket ที่ต้องการ State Connection ค้างไว้ตลอดเวลา ประยุกต์ใช้ Server-Sent Events (SSE) สำหรับการ Push สตรีมข้อความใหม่แบบ HTTP ปกติ ควบคู่กับ Adaptive Fallback Polling (15 วิ) สำรอง
3. ข้อกังวลด้านความปลอดภัยของรถยนต์และกฎหมาย PDPA ผู้โดยสารกังวลเรื่องการสวมทะเบียนรถ ขณะเดียวกันภาพถ่ายป้ายทะเบียนรถจัดเป็นข้อมูลระบุตัวบุคคลตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 สร้างระบบตรวจสอบภาพถ่ายป้ายทะเบียนรถโดยแอดมิน ร่วมกับการจัดทำ Vehicle PDPA Consent Modal บังคับยินยอมก่อนส่งข้อมูล และเก็บภาพเป็นความลับ
4. ปัญหา In-flight API Request Spams ผู้ใช้งานกดย้ำหรือเปลี่ยนแท็บบนหน้าเว็บอย่างรวดเร็ว ส่งผลให้เบราว์เซอร์ส่ง HTTP GET Request ข้อมูลเดียวกันซ้ำซ้อนในระดับมิลลิวินาที ออกแบบระบบ In-Flight Promise Sharing & Request Deduplication ในโมดูล API Client ตัดการยิงคำขอซ้ำซ้อนออกทั้งหมด

1. ระบบชำระเงินอัตโนมัติ (Automated Escrow Payment Gateway)

เชื่อมต่อ Payment Gateway ระดับองค์กร (เช่น Omise หรือ 2C2P) เพื่อตัดเงินและพักไว้ในระบบ Escrow กลาง และโอนเงินเข้าบัญชีคนขับอัตโนมัติเมื่อสิ้นสุดการเดินทางอย่างปลอดภัย

2. ระบบติดตามพิกัดรถสด (Live GPS Driver Tracking)

เชื่อมต่อ Geolocation API แบบความถี่สูง เพื่อให้ผู้โดยสารสามารถติดตามตำแหน่งรถของคนขับบนแผนที่ Google Maps ได้แบบสด ๆ (Real-Time) ในวันเดินทางจริง

3. การตรวจสอบภาพป้ายทะเบียนด้วย AI (AI-Powered OCR)

นำแบบจำลอง Computer Vision / OCR มาช่วยตรวจจับและอ่านตัวอักษรบนภาพถ่ายป้ายทะเบียนรถยนต์อัตโนมัติก่อนส่งให้ผู้ดูแลระบบ ช่วยลดเวลาในการตรวจสอบลงกว่า 80%

4. แอปพลิเคชันบนมือถือและระบบแจ้งเตือน (PWA & Web Push)

ต่อยอดระบบสู่ Progressive Web Application (PWA) ติดตั้งบนหน้าจอมือถือได้เสมือน Native App พร้อมระบบ Web Push Notification แจ้งเตือนแม้ผู้ใช้ปิดเบราว์เซอร์

สรุปบทส่งท้าย (Closing Remark)

โครงงาน Iko-Share พิสูจน์ให้เห็นว่าการผสานนวัตกรรมซอฟต์แวร์สถาปัตยกรรม 3-Tier ร่วมกับหลักการแบ่งปันต้นทุนที่เป็นธรรมและความใส่ใจในสิ่งแวดล้อม (ESG) สามารถสร้างสรรค์บริการสาธารณะดิจิทัลที่ตอบโจทย์วิถีชีวิตคนรุ่นใหม่ได้อย่างยั่งยืน ทั้งในมิติเศรษฐกิจ สังคม และสิ่งแวดล้อม
